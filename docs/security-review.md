# オンライン対戦の静的セキュリティレビュー

2026-11-24。リポジトリ内のルール・クライアントコードを確認した結果。
本番Firebase Consoleのルール、App Check、料金プラン、利用量は未確認。
本番データの改ざんや攻撃テストは実施していない。機能テストの成功は安全性の保証ではない。

## 優先して修正する問題

| 優先度 | 対象 | 発見した問題 | 想定する影響 |
| --- | --- | --- | --- |
| 高 | firebase-database.rules.json: rooms/$roomId/.write | 参加者ならルーム全体を書き込める。子のinput/$uid/.writeでは親からの許可を取り消せない | 同じ対戦の相手入力・手番・勝敗・参加者を書き換えられる。ルーム削除も防げない |
| 高 | matchmaking/queue/$uid/.write | 他人のwaitingをmatchedに変更する許可に、相互の参加関係や正当なルーム作成との結び付きがない | 待機の妨害や不正なルームへの誘導 |
| 中〜高 | ルーム作成・入力の制限 | 回数・サイズ・数値の範囲・参加人数の検証が不足。maxActiveRoomsはサーバー側の作成制限ではない | 大量作成・巨大なデータ・不正入力によるクォータ消費、対戦不能 |

匿名認証でauth != nullを満たせるため、ログイン済みという条件だけでは
対戦参加の正当性や操作権限を保証しない。
ルートの.read/.writeはfalseなので、DB全体が無条件に公開されていると断定はしない。
上記は記載されたルールが本番と同一の場合に成立する問題。

## 修正方針

1. 本番ルールとリポジトリ内のルールの差分を確認する。
2. ルーム全体の包括的な更新許可を外し、フィールド別の権限に分ける。
   自分の入力のみ更新、参加者IDは固定、ホスト用状態と各自の入力を分離する。
3. マッチ成立はキュー・ルーム・双方の参加関係を検証する。一意なマッチ確定や
   信頼できる勝敗が必要なら、サーバー側の処理を導入する。
4. 入力の数値範囲、配列長、文字列長、参加者数、状態遷移、更新頻度を検証する。
5. Emulator Suiteで未認証・無関係な第三者・対戦参加者ごとの許可/拒否をテストする。
6. App Check、利用量監視、プラン・クォータも確認する。App Checkだけでは不正を防ぎ切れない。

クライアントをホストとして物理計算させる現構成では、ルールを細分化しても
ホストのチートまで完全には防げない。競技性の保証には権威あるサーバーでの判定が必要。
UIのオンラインボタンを隠すだけではDBへの直接アクセスを止められない。

## 今回変更していないもの

本番・リポジトリのFirebaseルール、公開設定、料金プラン。
CPUの強化は端末内で完結し、これらの権限を広げない。
