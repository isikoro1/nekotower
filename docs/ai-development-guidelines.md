# AI駆動開発・ドキュメント管理ガイドライン

作成日：2026-11-24  
バージョン：1.0

## 1. 目的

特定のAIや会話履歴に依存せず、複数のAIを使い分けながら、個人開発アプリを継続的に開発・保守できる環境を構築する。

ソースコードだけでなく、コードを生み出すための要求、仕様、設計意図、制約、検証方法も開発資産として蓄積する。

目指す状態は、別のAIに切り替えたり、数カ月後に開発を再開したりしても、リポジトリを起点として開発を継続できることである。

## 2. 基本思想

- AIとの会話履歴を唯一の情報源にしない。
- 自然言語による要求や指示から、永続的な仕様・設計判断を抽出して保存する。
- ドキュメントとソースコードを同じGitリポジトリで管理する。
- AIが必要な情報だけを参照できるようにし、コンテキストとトークン消費を抑える。
- ドキュメントは必要最小限とし、維持すること自体を目的にしない。
- 重要な振る舞いは自動テストで保証する。

## 3. プロンプト・仕様書・設計書の役割

| 種類 | 役割 | 保存方針 |
| --- | --- | --- |
| プロンプト | 今回AIに何をしてほしいか | 再利用価値があるものだけ保存 |
| 仕様書 | アプリが何を実現し、どう振る舞うべきか | 継続的に管理 |
| 設計書 | 仕様をどのような構造で実現するか | 重要な構造・制約を管理 |
| 開発指示書 | AIが開発時に守るべきルール | 継続的に管理 |
| 設計判断記録 | なぜその技術や設計を選択したか | 重要な判断を管理 |
| 自動テスト | 実装が期待する振る舞いを満たすか | コードと一緒に管理 |

### 一時的な指示から永続的な仕様への変換

一時的なプロンプト：

> 画面をもう少しおしゃれにして。

永続的な仕様・制約：

- シンプルで洗練されたUIとする。
- 不要なキャッチコピーは表示しない。
- 既存機能を維持する。
- モバイルとデスクトップに対応する。
- 装飾やアニメーションによって操作性を損なわない。

主観的な要件は、必要に応じて承認済みの画面イメージや具体的な受入条件で補う。会話中の試行錯誤や撤回済みの案を、確定仕様として残さない。

## 4. 推奨リポジトリ構成

### 小規模アプリ（最初はこれで十分）

```text
my-app/
├── README.md        # 概要・起動・デプロイ方法
├── AGENTS.md        # AI共通の開発指示
├── docs/
│   └── spec.md      # 機能仕様・制約・受入条件
├── src/             # 実装（構成は技術スタックに応じる）
└── tests/           # 自動テスト
```

### 規模が拡大した場合

```text
my-app/
├── README.md
├── AGENTS.md
├── docs/
│   ├── spec.md
│   ├── architecture.md  # システム構成・責務・データフロー
│   ├── design.md        # UI/UX・デザイン方針
│   ├── decisions.md     # 設計判断とその理由（必要ならADRに分割）
│   └── roadmap.md       # 今後の開発予定・未解決課題
├── prompts/             # 再利用可能な指示テンプレートのみ
├── src/
└── tests/
```

すべてのファイルを最初から作成する必要はない。情報が増えて管理しにくくなった時点で分割する。

## 5. 複数AI間の一貫性とトークン節約

- 共通の仕様・設計情報は `docs/` に集約する。
- `AGENTS.md` は短く保ち、必要なドキュメントへの入口とする。
- AIツールごとに指示ファイルの読み込み方法は異なる。必要に応じてツール固有の設定から共通文書を参照させる。自動的に読まれると仮定しない。
- 作業に関係のある文書・コード・テストを優先して読み込む。毎回リポジトリ全体や会話履歴を投入しない。
- 同じ仕様を複数ファイルに重複して記載しない。
- 同時に複数のAIで作業する場合は、ブランチや作業範囲を分離し、差分レビューとテストを経て統合する。
- AIによって実装方法が異なることは許容する。ただし、要求された振る舞い、制約、公開インターフェースの一貫性は維持する。

## 6. 開発サイクル

1. 既存仕様・開発ルール・関連コードを確認する。
2. 要求を整理し、必要に応じて受入条件を定義する。
3. 変更範囲と影響を確認する。
4. AIを利用して設計・実装・テストを行う。
5. テスト結果とGit差分を確認する。
6. 確定した仕様や重要な設計判断をドキュメントへ反映する。
7. 実装・テスト・関連文書を整合した状態でコミットする。

仕様と実装が矛盾する場合、AIが独断でどちらかを正しいと決めない。意図的な仕様変更なのか、不具合なのか、文書の更新漏れなのかを確認する。

## 7. AGENTS.md に転用できる共通開発指示

以下を各リポジトリの開発ルールの出発点として使用する。

```markdown
# Development Instructions

## 作業開始時
- README.md、既存の開発指示、関連する仕様書を確認する。
- 対象機能のコードとテストを確認する。
- 不明な仕様を確定事項として扱わない。

## 実装時
- 既存機能と公開インターフェースの互換性を維持する。
- 要求に無関係な変更や大規模なリファクタリングを避ける。
- 不要な依存ライブラリや複雑な抽象化を追加しない。
- 保守性、可読性、テスト容易性を重視する。
- 認証情報や秘密鍵をコード・文書・ログに記録しない。

## ドキュメント管理
- 確定した機能追加や仕様変更は関連ドキュメントへ反映する。
- 重要な設計判断とその理由を記録する。
- 一時的な指示と永続的な仕様を区別する。
- 記述の重複を避け、ドキュメントを簡潔に保つ。
- 特定のAIや会話履歴に依存しない構成とする。
- 仕様と実装の矛盾を発見した場合は報告する。

## 検証と完了条件
- 重要な仕様は可能な限り自動テストで保証する。
- 関連するテスト・ビルド・静的解析を実行する。
- 実行できなかった検証とその理由を明記する。
- 変更内容、影響範囲、残課題を簡潔に報告する。
```

## 8. docs/spec.md のテンプレート

```markdown
# アプリ仕様書

## 目的
<!-- 何のために存在するアプリか -->

## 対象ユーザー・利用場面

## 機能仕様
### F-001: 機能名
- 入力：
- 処理・振る舞い：
- 出力：
- 異常時の振る舞い：
- 受入条件：

## 非機能要件・制約
<!-- 性能、互換性、セキュリティ、費用、対応環境など -->

## UI/UX方針

## 対象外・未確定事項

## 関連文書・テスト
```

受入条件は「何をもって完成とするか」を具体化する。例えば、タイマーアプリなら「一時停止中は残り時間が減少しない」「再開時に停止時点の残り時間から計測する」など、検証可能な形にする。

## 9. 既存アプリへ適用するためのプロンプト

```text
このリポジトリを、複数のAIで継続的に開発・保守できる状態に整備してください。

1. 既存コード、README、テスト、設定を確認してください。
2. 現在の実装から確認できる仕様を docs/spec.md に整理してください。
3. 推測した仕様や未確定事項は、確認済みの仕様と区別してください。
4. AGENTS.md に共通開発ルールと参照先を記載してください。
5. 重要な構造や設計判断がある場合のみ追加文書を作成してください。
6. 文書の重複を避け、必要最小限の情報にしてください。
7. 今回はドキュメント整備のみとし、アプリの機能やコードは変更しないでください。
8. 作成・更新したファイルと未確定事項を報告してください。
```

既存のドキュメントがある場合は、無条件に上書きせず、内容を確認して統合する。

## 10. AI時代のソフトウェアエンジニアリング

この方針は Spec-Driven Development（仕様駆動開発）に近い。仕様書は説明・合意形成のためだけでなく、AIによる実装を駆動する入力にもなる。

今後重視したい能力：

- **Specification Engineering**：曖昧な要求を検証可能な仕様に変換する。
- **Context Engineering**：AIに必要な情報を適切な粒度で提供する。
- **Software Architecture**：人間とAIが理解・変更しやすい構造を設計する。
- **Verification**：生成された実装の正しさを検証する。

自然言語の仕様は高い抽象度で意図を表現できるが、曖昧さを完全には排除できない。コード、型、スキーマ、自動テストと組み合わせて管理する。

## 11. 運用チェックリスト

- [ ] 別のAIでも会話履歴なしに開発を再開できる。
- [ ] 確定仕様と未確定事項を区別している。
- [ ] 重要な制約・設計意図が記録されている。
- [ ] 仕様と実装に認識済みの不整合がない。
- [ ] 重要な振る舞いに検証手段がある。
- [ ] 起動・テスト・デプロイ方法が分かる。
- [ ] 文書が必要最小限で、秘密情報を含まない。
- [ ] 変更履歴をGitで追跡できる。

## 結論

AIにアプリを作らせるだけでなく、AIが継続的にアプリを開発できる環境そのものを設計する。

コードだけでなく、コードを生み出すための知識そのものをバージョン管理する。
